La propuesta

Markdown + Quarto + Python + git
una narrativa computacional, versionada,
en un ambiente virtual aislado

La respuesta al caos anterior, en una línea. Markdown para escribir y para hablar con los agentes; Quarto para que el documento ejecute su propio código; Python para el cálculo; git para que cada cambio quede registrado, revisable y reversible; y todo dentro de un ambiente aislado y recreable (uv). “Narrativa computacional”: el proyecto se lee de principio a fin como una historia que corre.

¿Qué es Markdown?

Lo que escribes

# Resultados

El flujo **máximo** fue de 4.2 L/s
(ver [método](metodo.md)).

- medición directa
- modelo ajustado

Lo que se ve

Resultados

El flujo máximo fue de 4.2 L/s
(ver método).

  • medición directa
  • modelo ajustado
  • Lenguaje de marcado ligero (John Gruber, 2004): texto plano legible con marcas mínimas.
  • Separa contenido de formato; se versiona con git y los diffs se leen (a diferencia de un .docx).
  • Es el idioma nativo de GitHub y de los LLMs: README.md, PLAN.md, AGENTS.md.

La clave para esta charla: cuando hablas con un agente, hablas en Markdown. El plan, las reglas y la bitácora van a ser archivos .md dentro del repositorio.

¿Qué es Quarto?

  • Sistema de publicación científica y técnica de código abierto (Posit; sucesor de R Markdown).
  • Un .qmd = Markdown + bloques de código ejecutables (Python, R, Julia) + opciones en YAML.
  • Un mismo archivo fuente rinde a HTML, PDF (LaTeX), docx, diapositivas, sitios web y libros.
---
title: "Análisis de mediciones"
format: html
---

Los datos muestran un máximo en verano (@fig-serie).

```{python}
#| label: fig-serie
#| fig-cap: "Serie de tiempo de la medición"
df.plot(x="fecha", y="flujo_l_s")
```

Estas diapositivas están hechas en Quarto.

Señalar las tres piezas en el ejemplo: YAML arriba (opciones documentadas), texto en Markdown con referencia cruzada, celda de Python con etiqueta y pie de figura.

Por qué juntos: el análisis es el documento

El flujo de siempre

  1. Script que genera figuras
  2. Copiar y pegar al Word
  3. Cambian los datos…
  4. …repetir a mano y rezar

Texto y código divergen desde el día uno.

Con Quarto

  1. Texto, código, opciones y resultados en un solo archivo versionado
  2. Cambian los datos → quarto render
  3. Figuras, tablas y números se regeneran solos

El documento no puede mentir sobre su código.

Frase ancla: “el análisis ES el documento”. No hay un script por un lado y un Word por el otro. Esto es lo que vuelve auditable el trabajo hecho con IA: todo lo que la IA escribió está a la vista.

¿Qué es el versionado?

  • Todos hemos versionado a mano: tesis_final_por_fin_eso_espero.docx.
  • Un sistema de control de versiones —git— guarda la historia completa del proyecto: quién cambió qué, cuándo y por qué. Un solo archivo, todas sus versiones.
  • Cada commit es un punto de retorno: equivocarse deja de ser caro, y el diff entre versiones siempre se puede leer.
  • git es software libre; yo publico mis repositorios en GitHub, que es gratuito para la comunidad académica (GitHub Education).

El meme hace el trabajo: todos reconocen esa carpeta. git reemplaza los nombres de archivo por una historia con autor, fecha y mensaje de cada cambio. Precisión: git (el versionador) es software libre; GitHub es la plataforma que lo hospeda y da colaboración + respaldo, gratuita para estudiantes y docentes vía GitHub Education.

Todo empieza por el entorno: uv

uv init analisis-climalab          # proyecto + ambiente virtual + pyproject.toml
uv add pandas pyarrow matplotlib   # instala y FIJA versiones en uv.lock
uv run quarto render               # todo corre dentro del ambiente
  • Un solo gestor: proyecto, versión de Python y paquetes; el ambiente virtual deja de ser un trámite.
  • uv.lock registra versiones exactas: la misma ciencia en otra máquina.
  • El espacio nace con narrativa: pyproject.toml dice qué es el proyecto, uv.lock con qué corre, PLAN.md y AGENTS.md bajo qué reglas.
  • El contrato declara la herramienta: “instala con uv add, ejecuta con uv run” — el agente no improvisa un pip install fuera del ambiente.

Si el agente sabe con qué instalar, no contamina el sistema ni rompe el ambiente: cada paquete que agrega queda fijado en uv.lock y el commit lo registra.

Estructura propuesta

proyecto/
├── PLAN.md                # contrato + bitácora de IA + decisiones de la persona autora
├── AGENTS.md              # reglas del espacio de trabajo para el agente
├── pyproject.toml         # entorno fijado con uv
├── uv.lock
├── data/
│   ├── 001_raw/           # inmutable: los datos crudos nunca se tocan
│   ├── 002_intermediate/  # datos procesados
│   └── 003_results/       # resultados del análisis
├── src/proyecto/          # funciones importables, cada una con prueba
├── tests/                 # pruebas físicas (pytest)
├── analysis/
│   └── index.qmd          # la narrativa computacional del análisis
└── tex/                   # opcional: main.tex (el artículo); recibe las figuras
                           # y tablas .tex que index.qmd declara FINALES

Es una narrativa, no una receta: la estructura se adapta al proyecto y a sus datos. Lo que no cambia: crudos intocables · entorno fijado · funciones con pruebas · análisis en .qmd.

Recorrer de arriba a abajo: primero los contratos (PLAN, AGENTS), luego el entorno, luego datos con crudos intocables y resultados en data/003_results/, funciones probadas, el análisis en un solo index.qmd, y tex/ con el artículo. PLAN.md concentra también la bitácora de IA y las decisiones: por eso no hay docs/. Detalle para la demo: el parquet llegó como “ClimaLab_2026-04-08_2026-08-05 (1).parquet”, con espacio y “(1)”. Moverlo a data/001_raw/ con nombre limpio es parte de la narrativa; su origen y fecha quedan anotados en la sección Datos del PLAN.md.

La fragmentación: así se publica la figura incorrecta

 se analiza            se genera                se manda             se agrega            se publica
datos + código  ──►  figura_v2_FINAL.png  ──►  por correo  ──►  a mano en main.tex  ──►  el PDF
  • El análisis en una compu, el manuscrito en otra, y la figura viajando por correo: cada flecha es un paso manual, invisible y sin registro.
  • Si el dato cambia después del envío, el artículo conserva la figura vieja — y nadie lo nota hasta que está publicado.
  • Todos tenemos la anécdota del paper con la figura incorrecta. No es descuido: es la fragilidad del proceso.


La cura no es otra flecha: es un proceso continuo en un repositorio compartido,
que asegura la reproducibilidad y hace obvio cuándo algo se rompe —
todo comandado por uv run quarto render.

Contar aquí la anécdota propia (o invitar a la audiencia a recordar la suya). El contraste con la estructura anterior: allá cada flecha vive en el repositorio y se regenera con un comando; aquí cada flecha vive en un correo y en la memoria de alguien. Datos, código y resultados no deben fragmentarse entre computadoras y personas: quien llega clona, sincroniza y reproduce.

¿Qué es un agente?

Agente = LLM + un bucle de herramientas
(leer y escribir archivos, ejecutar comandos, correr pruebas)
que itera hasta cumplir una tarea.

  • A diferencia del chat, actúa sobre tu repositorio: crea archivos, corre código, ve los errores y se corrige.
  • Por eso necesita reglas (AGENTS.md) y un contrato (PLAN.md): sin ellos, optimiza “que no truene”, no “que esté bien”.
  • El ciclo: lee el plan → propone acción → ejecuta herramienta → observa el resultado → repite.

Diferencia clave con copiar/pegar desde el chat: el agente cierra el ciclo solo. Eso multiplica la velocidad y también multiplica el daño si no hay reglas. La mención de PLAN.md anuncia el bloque que sigue: el contrato.

Agentes en la nube y agentes locales

Nube — mi caso: Claude (Claude Code)

  • Modelos de frontera, los más capaces
  • Sin hardware propio
  • Costo por uso
  • Los datos salen de tu máquina: considerarlo con datos sensibles

Local — también uso Qwen3.8 27B (qwen3.8:27b-mlx)

  • Los datos no salen; sin costo por token
  • Exige hardware capaz: aquí corre vía MLX en Apple Silicon con memoria unificada amplia (o GPU con VRAM suficiente)
  • Rinde menos que los modelos de frontera

Ser honesto con la restricción local: no es gratis, se paga en hardware y en capacidad del modelo. La decisión es por proyecto, no ideológica. De palabra si sale en el Q&A: nube para el trabajo pesado; local cuando los datos no deben salir o para tareas acotadas.

PLAN.md: el contrato con el agente

# PLAN · Clima ClimaLab (abr–ago 2026)

## Objetivo
Caracterizar temperatura, radiación
y viento de la estación.

## Datos
climalab_2026-04-08_2026-08-05.parquet
172 433 filas · cadencia 1 min
tdb [°C] · rh [%] · ghi/dni/dhi [W/m²]
ws [m/s] · wd [°] · p_atm · rain_acc

## Herramientas
Instalar con `uv add`, correr con `uv run`.

## Pasos
1. Validar crudos con pruebas físicas
2. Huecos y NaN → data/002_intermediate/
3. Día típico, rosa de viento, GHI diaria

## Criterios de aceptación
- `pytest` pasa · GHI nocturna = 0
- Figuras regenerables con `quarto render`

## Bitácora y decisiones
Qué propuso la IA, qué decidió
la persona autora, y por qué.
  • Se escribe antes de pedir una sola línea de código.
  • Dice qué quieres de los datos: preguntas, variables, unidades, supuestos.
  • Y con qué: la sección de herramientas le dice al agente cómo instalar y ejecutar.
  • git commit del plan = firma del contrato.
  • Cada sección es una unidad de trabajo para el agente.
  • Es también la bitácora: las decisiones de la persona autora quedan en el repo, no en la memoria.

El corazón de la charla empieza aquí. El plan no es burocracia: es lo que convierte “hazme el análisis” en una secuencia de encargos verificables.

Cómo se escribe: el LLM propone, el humano corrige

El borrador de la IA puede traer supuestos erróneos —unidades, convenciones, casos límite— y corregirlos en el plan cuesta minutos; corregirlos en el código, días.

Demo en vivo 1 · ≤ 2 min “Escribe PLAN.md para caracterizar el clima a partir del parquet de ClimaLab.
No escribas código.”

Mensaje: la revisión más barata del proyecto es la del plan. Es el único momento donde corregir no implica reescribir nada. Errores esperables del borrador (no adelantarlos en pantalla): asume datos horarios (son minutales), promedia la dirección del viento aritméticamente, y no dice qué hacer con los NaN de p_atm (17 % de la serie). Leer el borrador en voz alta y corregirlos antes del commit.

Leer el diff: la unidad de revisión

El diff es la lista exacta de lo que cambió: líneas que salen (-) y líneas que entran (+). Con agentes es el instrumento de revisión: no relees todo el archivo, lees el cambio.

$ git diff src/proyecto/radiacion.py

 def ghi_diaria(ghi_w_m2):
     """GHI diaria en kWh/m² por día."""
-    wh = ghi_w_m2 * (1 / 60)               # cada muestra [W/m²] dura 1 min
-    return wh.resample("1D").sum() / 1000
+    return ghi_w_m2.resample("1D").mean() / 1000
  • El agente “simplificó” el cálculo… y cambió sum() por mean(): eso ya no es energía diaria [kWh/m²·día], es potencia promedio [kW/m²].
  • El código corre sin error y los números salen con pinta razonable: solo el diff lo delata.

Caso ficticio pero típico: el cambio compila, no truena y el número es plausible. Dos líneas rojas y una verde: leerlas toma veinte segundos y evita una figura incorrecta publicada. Prepara la demo que sigue (ahí se lee un diff en vivo) y conecta con las pruebas de más adelante: una prueba con respuesta conocida también lo habría cazado — diff y pruebas son redundancia deliberada.

Demo en vivo: ejecutar el plan, parte por parte

Nunca “hazme todo el análisis”.
Una sección del plan → código → render → leer el diff → commit.

Demo en vivo 2 · ≤ 3 min Con el agente, en analysis/index.qmd: la temperatura de ClimaLab en dos pestañas —
(1) promedio diario y (2) running mean de 30 días.
Las pestañas son para decidir con cuál me quedo, conservando ambas opciones en el mismo documento para discutirlas con mi equipo.

El truco de Quarto — un tabset:

::: {.panel-tabset}
#### Promedio diario
tdb.resample("1D").mean()

#### Running mean 30 días
tdb.resample("1D").mean().rolling(30).mean()
:::

Por eso importa aprender Quarto y conocer sus capacidades —tabsets, referencias cruzadas, opciones de celda, formatos—: no puedes pedirle al agente lo que no sabes que existe.

Una vuelta completa del ciclo, en vivo: pedir la sección al agente, ver el código aparecer, leer el diff, render. Las pestañas materializan una decisión de análisis sin destruir la alternativa: el documento conserva las dos vistas y el equipo decide viéndolas. El tabset lo pedí yo, no lo propuso el agente: conocer la herramienta define qué puedes exigir. Cada vuelta es pequeña: si algo sale mal, el diff es corto. Lo contrario de “Accept All”. Respaldo por si falla la red/el agente: captura del render ya hecho.

¿Qué es una prueba? Una respuesta conocida de antemano

La función (escrita por el agente)

# src/proyecto/energia.py
def calcular_energia(potencia_w, freq="1h"):
    """Potencia [W] → energía [Wh],
    agregada a la frecuencia freq."""
    paso = (potencia_w.index[1]
            - potencia_w.index[0])
    dt_h = paso.total_seconds() / 3600
    return (potencia_w * dt_h).resample(freq).sum()

La prueba (datos inventados por la persona autora)

# tests/test_energia.py
def test_energia_con_respuesta_conocida():
    # 1200 W constantes, 2 horas, cada minuto
    idx = pd.date_range("2026-01-01",
                        periods=120, freq="1min")
    potencia = pd.Series(1200.0, index=idx)

    energia = calcular_energia(potencia, freq="1h")

    # con papel y lápiz: 1.2 kW × 1 h = 1200 Wh
    assert (energia == 1200.0).all()
    assert energia.sum() == 2400.0
  • La persona autora inventa datos cuya respuesta conoce sin correr el código: potencia constante → la energía se calcula con papel y lápiz.
  • Si el agente toca la función y el total deja de ser 2400 Wh, pytest truena en el acto.
  • Eso es una prueba: una afirmación que no depende de confiar en quien escribió el código.

El ejemplo más claro del concepto: el ground truth lo pone la persona, no el código. Señalar la frecuencia del resample como parámetro: la misma prueba se puede repetir con freq=“15min” (300 Wh por cuarto de hora). Verificado: estos asserts pasan tal cual.

Las pruebas son parte del plan

Cada afirmación verificable del plan se convierte en una prueba física con pytest. Estas tres corren sobre los datos reales de ClimaLab, con el resultado real:

def test_radiacion_nocturna():        # PASA: el piranómetro está bien
    noche = df.between_time("22:00", "04:00")
    assert (noche["ghi"] == 0).all()

def test_rangos_fisicos():            # PASA: rh en [0, 100], ws ≥ 0
    assert df["rh"].between(0, 100).all()
    assert df["ws"].ge(0).all()

def test_serie_completa():            # FALLA: hay 2 huecos > 1 min
    saltos = df.index.to_series().diff()
    assert not (saltos > pd.Timedelta("1min")).any()
  • La prueba que falla no es un fracaso: obliga a decidir (¿interpolar?, ¿dejar el hueco?) y a documentar la decisión.
  • Las pruebas físicas detectan lo imposible; la referencia externa detecta lo plausible pero incorrecto.
  • Ojo con las pruebas tautológicas que proponen los LLM: prueban que el código hace lo que el código hace.

Aquí entra el “pruebas” del título. No son pruebas de software por cumplir: son las afirmaciones del plan convertidas en código que vigila al agente.

Esto ya tiene nombre: spec-driven development

Vibe coding (Karpathy)

  • El prompt es la especificación
  • El código no se lee
  • “Accept All”
  • Para proyectos desechables

Spec-driven (lo que acabamos de hacer)

  • PLAN.md firmado es la especificación
  • El agente ejecuta el spec; el humano lo escribe y lo verifica
  • Diff leído, pruebas pasando, commit
  • Para trabajo que se publica

Nombrar lo que ya hicimos en el bloque anterior: no inventamos nada, es la misma transición que está dando la industria del software con los agentes.

Cuando src/ crece: conviértelo en paquete

Si acumulas muchas funciones que reutilizas entre proyectos, el siguiente paso natural es un paquete instalable: documentado, versionado, citable.

Caso en casa: EnerHabitat en PyPI

uv add enerhabitat

  • De scripts de investigación a herramienta que cualquiera instala.
  • Las versiones quedan fijadas en el uv.lock de quien la usa: tu ciencia se vuelve dependencia reproducible de la de otros.

EnerHabitat: simulación de la transferencia de calor en envolventes, IER-UNAM. El mensaje no es “publiquen paquetes”: es que la estructura de este flujo (src/ + tests/) deja el paquete casi listo.

Recomendación a futuro: MCP

MCP (Model Context Protocol): estándar abierto para exponer tus funciones y datos como herramientas que cualquier agente puede invocar directamente.

  • Tiene sentido cuando tu código ya es biblioteca: muchas funciones probadas, quizá un paquete.
  • El agente deja de reescribir tus cálculos y pasa a llamarlos: menos código nuevo que auditar.
  • Es recomendación a futuro, no requisito del flujo de hoy.

Un minuto, sin demo. La idea que debe quedar: la trayectoria natural es funciones → paquete → herramientas MCP, y cada paso reduce lo que el agente improvisa.

Saber programar es la licencia de conducir

A

Auditar

Sin leer código no puedes revisar lo que el agente escribe: el diff es tu instrumento.

B

Entender

El criterio de dominio decide si el número es plausible; la IA no sabe lo que no le dijiste.

C

Guiar

Human in the loop: el plan, las correcciones y la firma son humanas. La IA no firma.


La IA sube el piso; el techo —criterio, verificación, firma— sigue siendo humano.

Datos sensibles: “¿Se pueden usar estos agentes cuando los datos no pueden salir de la institución?” (→ diapositiva nube vs local, Qwen/MLX). 2. Autoría: “Si el agente escribió el código y tú lo revisaste, ¿quién es el autor? ¿Hay que declararlo a la revista?” (→ bitácora en PLAN.md; la persona firma; revisar política de IA de la revista). 3. Verificación: “Si el agente escribe el código Y las pruebas, ¿quién vigila al vigilante?” (→ pruebas tautológicas; ground truth de la persona autora; diff + pruebas = redundancia deliberada). 4. Formación: “¿No les atrofia el aprendizaje a los estudiantes?” (→ leer diffs es leer código experto a diario; lo que atrofia es “Accept All”; licencia de conducir).
